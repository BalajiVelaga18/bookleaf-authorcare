# Submission Approach

## What was prioritized

The implementation focuses first on the features that directly satisfy the assignment's acceptance criteria:

1. Correct seeding of all 10 authors and 18 books with preserved nulls and relationships.
2. Secure JWT authentication with role-based access control and resource ownership.
3. Complete ticket lifecycle: creation, classification, admin workspace, public replies, internal notes, status/assignment.
4. Real Google Gemini integration for classification and response drafting, with structured output and fallbacks.
5. Near-real-time updates via SSE.
6. Polished, responsive UI for both portals.

## Architecture decisions and trade-offs

- **Monorepo layout** keeps frontend and backend together for easy submission while remaining independently deployable.
- **Mongoose + MongoDB Atlas** provides flexible schemas that map well to the provided JSON dataset.
- **JWT in httpOnly cookies** balances security and simplicity; CSRF risk is reduced through `SameSite` and origin-restricted CORS.
- **SSE** provides enough real-time capability without the operational overhead of WebSockets or a message broker.
- **Controllers + services + models** separation keeps AI prompt logic isolated and testable.

## AI integration strategy

- Gemini calls are made only from the backend using the official `@google/genai` SDK.
- Classification happens once on ticket creation and can be regenerated by an admin.
- Draft generation is on-demand from the admin ticket workspace.
- Prompts are versioned as code, include only relevant context, and enforce JSON schema output.
- A dedicated knowledge-base module captures BookLeaf policies accurately.
- If Gemini is unavailable, the application degrades gracefully: tickets save, admins can classify manually, and replies can be written by hand.

## Important limitations

- File attachment UI is present but upload/storage is not implemented.
- Email/push notifications are not implemented; updates rely on SSE and polling fallback.
- Deployment was prepared but not executed because no live hosting credentials or MongoDB Atlas URI were available in this environment.
- Backend integration tests are written but require a MongoDB URI to run.

## How the system could evolve into a production platform

- Add file upload handling with S3-compatible storage and virus scanning.
- Introduce email/SMS notifications for critical tickets and payout events.
- Add a notification center and in-app inbox.
- Implement agent workload balancing and ticket reassignment workflows.
- Add audit dashboards, SLA tracking, and AI usage/cost analytics.
- Migrate to a dedicated message queue (e.g. Redis Pub/Sub) for horizontal scaling of SSE.
- Add end-to-end frontend tests with Playwright.
